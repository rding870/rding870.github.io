Making VITRA-VLA inference 6.8× faster

Profiling a vision-language-action model one bottleneck at a time, from 160.5 ms to 23.6 ms per prediction.

Recently, I've been interning at Human Archive, where the team has been experimenting with different datasets and training various models using VITRA for their latest release. I got curious about whether I could make inference faster, so I decided to try optimizing it myself. This post documents my attempts and what I learned along the way.

Baseline and profiling

The first thing I did was profile and benchmark VITRA-VLA to understand where the inference time was going. The model uses a vision encoder, a Gemma language model, and a diffusion transformer (DiT) that generates robot actions through 10 denoising steps. My baseline (FP32, eager mode) took 160.5 ms per prediction on an RTX 6000 Ada.

CUDA Graphs

From profiling, I noticed that a significant amount of time was being spent on the CPU launching GPU kernels. Even though the GPU operations themselves were relatively fast, the CPU had to repeatedly tell the GPU what to execute, which introduced overhead.

To fix this, I implemented CUDA Graphs for the vision encoder, Gemma, and the DiT forward pass. CUDA Graphs basically record a sequence of GPU operations so that instead of the CPU launching each kernel individually, it can replay the entire sequence with a single graph launch. To do this, I first run the computation with fixed input shapes to warm up the model, then capture the GPU operations into a graph that can be reused for subsequent predictions.

This reduced CPU launch overhead and brought latency from 160.5 ms to 128.4 ms (1.25× faster), with output identical to the baseline.

BF16 mixed precision

After profiling and benchmarking again, I found that FP32 general matrix multiplications (GEMMs) were another major bottleneck, particularly in the DiT.

FP32 represents each number using 32 bits, or four bytes. This becomes expensive in large neural networks because moving weights and performing matrix multiplications requires substantial memory bandwidth and computation.

To address this, I switched to BF16 mixed precision. BF16 uses 16 bits, or two bytes, per number, reducing memory usage and allowing the GPU to use faster Tensor Core operations. BF16 autocast alone took latency from 128.4 ms to 68.9 ms (1.86× faster), the largest single gain.

However, BF16 has less numerical precision than FP32, so I needed to make sure the optimization didn't significantly change the model's predictions. I compared the resulting hand trajectories against the FP32 baseline. They moved by about 1.1 mm on average and at most 5.9 mm. Simply running the FP32 model with a different random seed moves them by about 28 mm on average and up to 131 mm, so the precision tradeoff was acceptable.

I also experimented with storing model weights directly in BF16 rather than relying only on BF16 autocast. This removed the repeated conversion of FP32 weights during inference and took latency from 68.9 ms to 40.4 ms (1.71× faster), with output identical to autocast. Together, the two BF16 steps gave a 3.2× speedup.

Skipping the unused vocabulary projection

The original model also computed Gemma's vocabulary logits (the lm_head), even though only the final hidden states are used. Skipping it took latency from 40.4 ms to 37.6 ms (1.07× faster), with identical output.

torch.compile

I also used torch.compile to optimize the DiT, including its forward_with_cfg function, which runs the diffusion transformer and combines the conditional and unconditional predictions for classifier-free guidance, as well as Gemma.

Unlike CUDA Graphs, which reduce the CPU overhead of launching GPU operations, torch.compile optimizes the computation itself. It analyzes PyTorch operations and can fuse multiple operations into fewer GPU kernels, reducing intermediate memory accesses and kernel launch overhead.

I initially tried torch.compile as a general optimization rather than targeting a specific bottleneck identified through profiling. I benchmarked it afterward to see whether it actually improved performance: it took latency from 37.6 ms to 25.6 ms (1.47× faster).

GPU preprocessing

Finally, I moved image preprocessing from the CPU to the GPU, which took latency from 25.6 ms to 23.6 ms (1.08× faster).

Overall, I reduced VITRA-VLA inference latency from 160.5 ms to 23.6 ms, achieving a 6.8× speedup and an 85% reduction in latency. The biggest takeaway was learning to profile after each optimization, because removing one bottleneck often revealed another.
